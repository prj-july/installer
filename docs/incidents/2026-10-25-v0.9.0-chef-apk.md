# v0.9.0 oven boot loop — incident report (2026-10-25)

**Status:** root cause confirmed offline from the released artifacts. Not yet
reproduced on our own hardware (no oven attached to the build workstation on
2026-10-25). v0.9.0 must be withdrawn and replaced before anyone else installs
it.

**Reporter:** Brooks Bennett (beta tester), 2026-10-25 12:38 PT:

> I restored to both my original backup as well as the working .7 version and
> tried to go to .9 from both. They both went to the boot loop. When restoring,
> the oven gets to 100% and stays a long time, but ultimately succeeds. [...]
> I am going to hold until you test that .9 is working.

Two separate problems are in that report. The boot loop is this document. The
"100% then 0 S LEFT" restore display is a cosmetic bug, fixed separately (see
the last section).

## One-line root cause

The Chef APK baked into v0.9.0 is **resource-incomplete**: its `resources.arsc`
names 35 resource files that are not in the APK (they exist only under a
differentletter case). The installer swaps that APK into
`/system/priv-app/Chef/Chef.apk` before Android starts; Chef — the oven's
cooking UI — cannot load those resources, the kiosk app crash-loops, and the
oven appears to boot-loop. v0.7 is unaffected because the build it bakes is
complete.

## Evidence (all offline, from the released artifacts)

The APK that v0.9.0 bakes is `Chef_cookmodes_foodack_signed.apk`, sha256
`be5ff47e054350975e6ab71ab1d5a71bcd0d409210dc89f447d4d9d15a415e1d`
(the same bytes are in the ISO payload as
`installer/liveiso/assets/Chef_cookmodes_signed.apk`, and in the signed wireless
update repo as `oven-updates/stable/artifacts/Chef_cookmodes_foodack_signed.apk`).

`scripts/check_apk_resources.py` (added with this report) gives:

| APK | zip entries | `res/` entries | paths named by `resources.arsc` | paths missing from zip |
|---|---|---|---|---|
| stock `Chef.apk` (healthy-build extraction) | 1609 | 614 | 614 | **0** |
| `Chef_cookmodes_signed.apk` 8a006b80… (what v0.7 bakes and installs) | 1609 | 614 | 614 | **0** |
| `Chef_cookmodes_foodack_signed.apk` be5ff47e… (what v0.9.0 bakes) | 1535 | 579 | 614 | **35** |

The 35 missing paths are exactly the lower/mixed-case halves of case-only
pairs, e.g.:

```
resources.arsc wants   the zip has only
res/Qv.png             res/QV.png
res/Rq.xml             res/RQ.xml
res/ca.9.png           res/CA.9.png
res/eB.9.png           res/Eb.9.png
res/ee.png             res/Ee.png
res/aA.xml             res/AA.xml
... 35 in total
```

June's stock Chef APK legitimately contains *both* names (`res/Rq.xml` **and**
`res/RQ.xml`); Android/zip are case-sensitive. The foodack rebuild collapsed
each case-only pair, so only one variant survived. The entry-count arithmetic
confirms it is a rebuild accident, not a different app: the foodack APK is
missing exactly 74 entries versus the good build — the 35 case-collapsed `res/`
files plus 39 `META-INF/*.version`/gradle metadata files — and has **zero**
entries the good build does not have. `resources.arsc` and `AndroidManifest.xml`
are byte-identical (same size and CRC) between the foodack APK and the good
build, so the dex/smali changes are the only intended difference.

Signature of the cause: this is what a rebuild on a **case-insensitive
filesystem** (Windows/SMB) does to an APK that has case-only duplicate resource
names. All eight other APKs baked into v0.9.0 pass the check with 0 missing; the
Chef APK is the only broken artifact.

The ISO payload is the assembled `installer/liveiso/assets/` directory verbatim
(`Dockerfile` `COPY assets`, then `rsync -a` into `/opt/june-installer` in
`build.sh`; `prepare_assets.sh` uses plain `cp` with no newline normalisation),
so these are the bytes that shipped. Cross-check against the previous ISO: the
v0.8.1 payload's Chef APK is the clean `8a006b80…` build, and v0.8.1 → v0.9.0
changes in the payload are the Chef swap plus the updater plumbing
(`updater.json`, `june-wireless-update`) — the boot-looping APK is the only APK
that changed.

## Why that produces a boot loop

`onoven/june_reaper.sh.junelocal` runs before Android starts. With a Chef stage
present it mounts the encrypted collector read-write and compares/copies the
staged APK over `/system/priv-app/Chef/Chef.apk` (v0.9.0 reaper lines
411–448). The swap succeeds (the zip is valid and the copy verifies), so
`/data/june/logs/chef_patch.log` will read `applied: be5ff47e…`. Android then
starts with a Chef build whose resource table points at files that are not
there. On the first `Resources` lookup for one of those drawables/layouts
(9-patch PNGs and XML layouts are exactly the kind of resource the idle UI
draws), the process throws `Resources$NotFoundException`/`InflateException`;
as a kiosk/priv-app the UI is restarted, and the oven never reaches a usable
screen. On a v0.7 install the same code path installs 8a006b80…, which is
complete, so the oven boots.

The failure is deterministic and independent of the previous disk state, which
matches the report: restoring the original image or the working .7 image both
lead to the same boot loop, because the destructive step is the v0.9.0 install
itself.

## Why the release process did not catch it

Every check the release did was about the ISO, not about the APK's internals:
SHA-256 of the ISO, file presence inside the squashfs, CRLF checks, and the
Chef hash matching the signed manifest. v0.8 and v0.8.1 were built and tagged
but never published, and no 0.8-lineage build had ever been installed on a
physical oven — so v0.9.0 was the first install of the new foodack Chef build
anywhere. There was no check comparing `resources.arsc` with the zip.

## Blast radius

* **Installer download.** `https://downloads.project-july.org/installer/latest.json`
  currently serves `v0.9.0` (sha256 `1db07327…be98`, size 1,416,314,880) — the
  same ISO that fails here. Every new download and every "Update the installer"
  in June USB gets it.
* **Wireless updates.** `https://downloads.project-july.org/oven-updates/stable/manifest.json`
  is live (release `2026.10.24-chef-foodack`, sequence `2026102401`, published
  2026-10-25T06:47Z) and names the same broken APK
  (`be5ff47e…`). Any oven that reached "Check for update" would download it and
  apply it at the next boot — the same failure, without the installer. It is
  currently inert only because no 0.9.0 oven boots far enough to check.
* **Last known-good public release:** v0.7 (2026-10-11, build
  `20261011-1353-1d65c317`). v0.8/v0.8.1 were never uploaded.
* **Reporter's oven:** recoverable — his restore path is proven (he restored
  twice). No factory reset needed.

## Immediate actions (in order)

1. **Stop serving v0.9.0.** Point `/installer/latest`, `latest.json` and the
   website "Current build" back to v0.7 (or take the installer download down).
   Do not leave a build that boot-loops as "latest".
2. **Withdraw the broken oven update.** Remove
   `/oven-updates/stable/{manifest.json,manifest.sig,artifacts/}` (oven-updates
   is not serving anyone useful yet), or publish a new higher sequence
   (`2026102402`) whose `chef` artifact is a *verified* APK. Do not leave
   `be5ff47e…` reachable from any published manifest.
3. **Tell the tester to restore his verified .7 backup and stay there** until we
   ship a hardware-tested build.
4. **Build v0.9.1 without the broken APK.** Either
   * rebuild the foodack Chef APK on a case-sensitive Linux filesystem from the
     clean stock `Chef.apk` (the builder's apktool work dir must stay on ext4 —
     never decode/rebuild on the SMB/Windows tree), then:
     `python3 scripts/check_apk_resources.py <new.apk>` → must print
     `missing: 0`; or
   * ship v0.9.1 with the previously good builder by pointing the payload at it:
     `JUNE_CHEF_APK=…/Chef_cookmodes_signed.apk` (sha256 `8a006b80…`).
   `prepare_assets.sh` now refuses to bake an APK that fails the check, so a
   build with `be5ff47e…` will stop with an error.
5. **Hardware smoke test before publishing** — one on-oven install of the exact
   ISO (restore → install → boot → `http://<oven-ip>/local` shows the status
   page). This has to become a release gate; v0.8.x never got it and this
   incident is the result.
6. Then publish v0.9.1 + release notes that say v0.9.0 is withdrawn.

## Permanent fixes added to this tree (uncommitted)

* `scripts/check_apk_resources.py` — new release gate: verifies that every
  `res/...` path named by `resources.arsc` exists in the APK at exact case
  (plus zip CRC, `AndroidManifest.xml` and dex presence). Point it at any APK;
  exits non-zero and names the missing files.
* `installer/liveiso/prepare_assets.sh` — after copying the Chef APK into the
  payload, runs the gate and aborts the build on failure.
* `scripts/verify-release.sh` — runs the gate over every
  `installer/liveiso/assets/*.apk` when a payload has been assembled (e.g. in
  CI).

## Reproducing the check

```sh
# broken (v0.9.0): exits 1, names the 35 files
python3 scripts/check_apk_resources.py \
  installer/liveiso/assets/Chef_cookmodes_signed.apk

# good (v0.7 bake): exits 0
python3 scripts/check_apk_resources.py \
  apk-patches/chef-cookmodes/Chef_cookmodes_signed.apk
```

## Optional evidence from the reporter's oven (to close the loop on hardware)

* `adb shell cat /data/june/logs/chef_patch.log` → expect `applied: be5ff47e…`.
* `adb shell sha256sum /system/priv-app/Chef/Chef.apk` → expect
  `be5ff47e…` (confirms the broken APK is the live one).
* `adb logcat -b all -d | grep -E 'AndroidRuntime|Resources|Chef'` → expect a
  `Resources$NotFoundException` / `InflateException` stack from
  `com.junelife.device.chef`.
* If `adb devices` never lists the oven, the failure is earlier than the
  framework: capture the `J2` RS-232 console instead (see
  `local-resources/june-arch/docs/hardware/rcm-arch-laptop-runbook.md`).

None of this is required to act — the artifact defect is proven — but it is the
cheapest way to confirm the crash mechanism on a real oven if one is in the
loop.

## What is still unknown

* Not yet reproduced on an oven we control. The defect and its mechanism are
  proven at the artifact level; the exact crashing resource/exception has not
  been captured from hardware.
* Whether v0.8's identity self-heal, per-home CA and JuneDns changes are
  otherwise safe: v0.8/v0.8.1 never ran on hardware. The v0.9.1 rebuild will be
  the first 0.8-lineage install to be tested; watch the release-notes checks
  (`/local` status, `identity_ensure.state`, cook status, pairing).

## Related, separate fix: "WRITE OVEN STORAGE — 0 S LEFT"

Brooks's restore-progress complaint is real and cosmetic. GNU `dd` emits one
final 100% progress record *before* `conv=fsync` flushes the write and prints its
summary after the flush, so the byte-only ETA reads 0 s for the whole
multi-minute flush. The GUI now shows a **finishing** phase at 100% (no fake
ETA, ticking clock, "do not unplug"), and states the 15–30 minute expectation
before a restore/backup starts. Files: `installer/liveiso/gui/server.py`,
`installer/liveiso/gui/web/app.js`, `installer/liveiso/gui/web/app.css`,
`installer/liveiso/gui/dev/progress_selftest.py`, `USE_LIVE_INSTALLER.md`.
The text-mode menu has the same 0 s display (`build.sh`) and is a follow-up.
