# v0.9.1 wireless updates are unusable on hardware (2026-10-26)

Hardware test of the signed wireless updater on the installed v0.9.1 oven.
Result: **the updater cannot reach `downloads.project-july.org` at all.** Both
blockers are in the on-oven Go client (`june-local`), not in the release
repository. The fix cannot be delivered by a wireless update, because the
wireless update path is the thing that is broken — v0.9.2 must go out on a USB
installer.

## Test environment

| | |
|---|---|
| Oven | `192.168.1.207` (hostname `june2`, `june2.local`), reachable on 80/443 |
| Installer | v0.9.1, build `20261025-1411-b827be42`, `install.mode=basic`, `ca_mode=project` |
| Payload | `june-local` sha256 `85d86e9e…` (reports `version: 0.9.0` — see below), `Chef_cookmodes_signed.apk` sha256 `8a006b80…` |
| Update config | `/system/etc/june/updater.json`, key `k8J11cq1…`, channel `stable`, `min_sequence 2026102501` |
| Control token | generated at install, preserved in `/data/june/updates/control-token`; also printed in the install log (the USB copy is broken, see below) |

## What works

- Install is healthy: every component hash in `/local/status` matches
  (`install.components[].ok` all true), Chef is the known-good `8a006b80…`
  build, so the v0.9.0 Chef boot-loop regression is genuinely fixed on hardware.
- Updater config is present and enabled:
  `GET /local/update` → `{"configured":true,"enabled":true,"channel":"stable",
  "target":"june-oven-android5","state":"ready","current_sequence":2026102501}`.
- Control-plane gating behaves as designed:
  - `POST http://oven/local/update/check` → **426** "update controls require HTTPS".
  - `POST https://…/check` with no token or a wrong token → **401**.
- The live release repository itself is fine: `manifest.json` (sequence
  `2026102401`) and `manifest.sig` were fetched and the Ed25519 signature
  verified against the baked public key, using the updater's User-Agent
  (`june-local-updater/0.9.0`) — Cloudflare answers 200 (it 403s only
  `Python-urllib`), and the chain is `Cloudflare SNI leaf ← GTS WE1 ← GTS Root R4`.

## Failure 1 — no DNS resolver (observed)

`POST /local/update/check` with the real token:

```
HTTP/1.1 502 Bad Gateway
{"success":false,
 "error":"fetch manifest: Get \"https://downloads.project-july.org/oven-updates/stable/manifest.json\":
          dial tcp: lookup downloads.project-july.org on [::1]:53: read udp [::1]:58818->[::1]:53:
          read: connection refused"}
```

Root cause: `june-local` is built with `GOOS=linux GOARCH=arm CGO_ENABLED=0`
(`installer/golocal/Makefile:18-20`). A static Go binary on Linux resolves
names with the **pure Go resolver**, which reads `/etc/resolv.conf`. Android 5
does not have one — DNS is delivered to bionic through netd/properties
(`/system/etc/dhcpcd/dhcpcd-hooks/20-dns.conf` only sets `dhcp.<iface>.dnsN`).
With no nameserver lines Go falls back to its compiled-in `defaultNS`
(`127.0.0.1:53`, `[::1]:53`), which is exactly the error above.

Confirmed by the oven's own status JSON: `network` has **no `dns` and no
`gateway` keys** (`golocal/status.go:542-552` reads `/system/etc/hosts` and
`/etc/resolv.conf`); `problems` is `null`, so the status page does not flag it.

This is not specific to this oven or this LAN: any 0.9.x oven would fail the
same way.

## Failure 2 — empty root store (next failure, from source + image)

Even with DNS fixed, TLS verification will fail on the same class of problem:

- The binary is `GOOS=linux`, so `crypto/x509/root_linux.go` only reads the
  Linux bundle paths (`/etc/ssl/certs/ca-certificates.crt`, …) and adds the
  Android store (`/system/etc/security/cacerts`) only when the binary itself is
  built for Android (`goos.IsAndroid`). It is not.
- A captured stock oven `/system/etc` (2026-09-24 image under
  `local-resources/june-arch/capture/`) contains neither `resolv.conf` nor an
  `ssl/` directory, and the frozen 2015 trust store would not contain the
  Cloudflare chain's root anyway (`GTS Root R4`).
- Net effect: `x509.SystemCertPool()` is empty → manager fetch fails with
  `x509: certificate signed by unknown authority`.

So the v0.9.x updater has **two** independent environment assumptions that
never held on the oven. Neither unit nor "end-to-end" test could catch them:
`TestPublishedRepositoryEndToEnd` serves the repo from `httptest` (plain HTTP)
with `AllowInsecure: true` and `SkipPlatform: true`.

## Secondary findings

1. **The token is never saved to the USB.** `onoven/deploy_onoven.sh:849`
   writes `/june-logs/update-token.txt` only when `/media/ventoy` exists, but
   the live installer mounts the Ventoy data partition at `/mnt/june-ventoy`
   (`installer/liveiso/prepare_assets.sh:1136`; install log:
   "Installer log saved to /mnt/june-ventoy/june-logs/…"). On this install the
   token was printed in the log but `update-token.txt` was absent from the USB.
   Recovered for the test from `F:\june-logs\june-install-20261026-025241.log`.
2. **Version string lies on 0.9.1.** The payload `june-local` was not rebuilt,
   so `/local/status` reports `version: 0.9.0` while `install.installer_version`
   is `0.9.1`. Testers and support will read "0.9.0" and conclude the install
   failed. Rebuild the binary with `VERSION=0.9.2`.
3. **HTTPS-by-IP does not validate.** In `basic` installs the served cert is
   `CN=api.junelife.com` with SANs `*.junelife.com`, `june.local`, `june2.local`,
   `june3.local` — **no IP SAN** (`cert.san_covers_current_ip=false`). Browser
   and `june-wireless-update -oven https://<ip>` both fail hostname
   verification, yet `WIRELESS_UPDATES.md` documents exactly that URL. Use
   `https://june2.local` (mDNS or a local DNS entry), or add a `-server-name`
   option to the client.
4. **Status page hides the failure class.** Missing resolver / empty root store
   is not reported in `problems`; the user only sees the raw `last_error` in
   Software updates. Add problem entries for "no DNS resolver for the updater"
   and (if detectable) "no usable CA bundle".

## Fix checklist for v0.9.2 (USB required)

`golocal` (june-local):

- [ ] Install a resolver that works on Android 5 before any updater HTTP client
  is built: read `net.dns1`…`net.dns4` (fallback `dhcp.<iface>.dnsN`, then the
  default gateway from `/proc/net/route`) via `getprop`, and override
  `net.DefaultResolver` with `PreferGo: true` and a `Dial` that points at that
  server (Go writes the query to the returned conn, so the address passed in
  can be ignored). Refresh lazily so a Wi-Fi reconnect is picked up.
- [ ] Give the updater client explicit roots: embed a Mozilla-derived bundle
  (`//go:embed`, e.g. `certs/roots.pem`) and set
  `TLSClientConfig.RootCAs` on the updater transport. Gate the bundle in
  `verify-release.sh` (must contain `GTS Root R4` and, since Cloudflare can
  rotate, the full current bundle). System-pool fallback stays for non-oven
  builds.
- [ ] Report resolver + CA-bundle state in `/local/status`, and flag missing
  DNS/roots under `problems`.
- [ ] Rebuild with `VERSION=0.9.2` (fixes finding 2).

`onoven` / installer:

- [ ] Token export: detect the Ventoy mount (`/mnt/june-ventoy`, `/media/ventoy`,
  or `backup.sh ventoy-dir`) instead of hardcoding `/media/ventoy`.
- [ ] Keep `min_sequence 2026102501` in `onoven/updater.json` for 0.9.2 so the
  first wireless update (sequence `2026102502`) is *offerable* on the fixed oven.
- [ ] Docs: use `https://<name>.local` (not the IP) for update controls, and
  note the IP-SAN limitation for basic installs.

## Acceptance test after 0.9.2 (with `2026102502` published)

Release `2026.10.26-chef-cookmodes`, sequence `2026102502`, artifact = the same
verified `8a006b80…` Chef APK (byte-identical to the 0.9.1 baseline, so boot
apply takes the `already-applied` path — no functional delta, no brick risk).

1. Reinstall 0.9.2 over the existing `/data` (no restore) → keep pairings and
   the token. Verify `/local/status`: `version.version=0.9.2`,
   `network.dns` lists the LAN resolver, `update.state=ready`,
   `current_sequence=2026102501`.
2. `https://june2.local/local` → Software updates → **Check for update**:
   expect `state=update-available`, `available.sequence=2026102502`,
   `last_error` empty. (This is the first time the manifest fetch works on an
   oven.)
3. **Stage for next boot** → expect `state=staged`, `pending.sequence=2026102502`,
   ~247 MB downloaded and SHA/ZIP-verified.
4. Power-cycle the oven → boot applier promotes the transaction: expect
   `state=up-to-date`, `current_sequence=2026102502`, `current_release=2026.10.26-…`,
   and `/data/june/logs/chef_patch.log` = `already-applied`.
5. Check again → `up-to-date` (equal sequence is not re-offered).
6. Negative controls (can be run before publishing 2502): the live channel's
   older `2026102401` manifest must not be offered once the fetch path works;
   scratch repo tests cover bad signature, size/SHA mismatch, missing artifact.
